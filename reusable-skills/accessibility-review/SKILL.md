# Accessibility Review

An AI-powered accessibility auditor that reads tool-generated reports, cross-references the
source code, and delivers a ranked issue list with WCAG 2.2 A/AA mapping, concrete proposed
fixes, and a confidence rating for each finding.

> **Read-only**: this skill inspects and reports only. It must never modify any source file.
> All proposed fixes are written to the output markdown as diff-style recommendations — the
> developer applies them manually after reviewing.

## Reference files

- `references/tool-parsers.md` — how to extract failures from Lighthouse, axe, pa11y, and WAVE
  report formats. Read this during Step 1 and keep it in context through Step 2.
- `references/wcag22-criteria.md` — WCAG 2.2 SC numbers, names, levels, and tag→SC mappings.
  Read this during Step 3.

---

## Workflow — follow these steps in order

### Step 1 — Discover inputs

Look for two categories of input, working from any paths the user provides or by searching
the workspace:

**A. Tool report files** — common locations and formats:

| Tool | Typical file | Format |
|------|-------------|--------|
| Lighthouse | `*.json` with `lighthouseVersion` key | JSON |
| axe-core / axe DevTools | `*.json` with `violations` array | JSON |
| pa11y | `*.json` with `issues` array or `*.csv` | JSON / CSV |
| WAVE | exported `*.json` with `categories` key | JSON |
| Deque WorldSpace | `*.json` | JSON |

Read `references/tool-parsers.md` to understand how to extract failures from each format.

**B. Frontend source code** — HTML templates, JSX/TSX, Angular templates, Vue SFCs, CSS/SCSS,
JavaScript/TypeScript. Identify the framework (Angular, React, Vue, plain HTML) and note
relevant files for each issue. Do **not** read every file upfront — load files on demand as
you investigate each issue.

If no report files are found, note this and proceed to a purely code-based review, flagging
that findings will have lower confidence without tool corroboration.

---

### Step 2 — Parse and normalise all report failures

For every failing audit across all report files:

1. Extract: rule ID, description, impact level (critical / serious / moderate / minor),
   WCAG tags, list of failing elements (selectors, snippets), and which page/URL it came from.
2. **Group** failures by rule ID across pages — a rule failing on 4 pages is one issue with
   4 affected locations, not 4 separate issues.
3. Note which pages are affected so the scope is clear.

Apply the extraction logic from `references/tool-parsers.md` (loaded in Step 1).

---

### Step 3 — Map each failure to WCAG 2.2 A/AA

Read `references/wcag22-criteria.md`.

For each grouped failure:

- Identify the primary WCAG 2.2 success criterion (SC) by number and name, e.g.
  *4.1.2 Name, Role, Value*.
- State the conformance level: **A** or **AA**.
- If the tool reports an older WCAG tag (e.g. `wcag412`), map it to the 2.2 SC using the
  reference file — most criteria carry over unchanged; note any that were added or changed
  in WCAG 2.2.
- If a finding doesn't map to any WCAG 2.2 SC, label it **Best Practice** and exclude it
  from the conformance summary but still include it in the report.

---

### Step 4 — Cross-reference with source code

For each grouped issue, find the relevant source file(s):

- Use the element selectors and snippets from the report to locate the template or component.
- Confirm the issue is present in the current source (reports may have been captured against
  a built/deployed version — source should match, but flag mismatches).
- Identify the exact file path and, where possible, the line or region to change.
- Note if the issue appears to be generated by a third-party library or directive (e.g. a
  UI Bootstrap typeahead injecting invalid ARIA) versus hand-written code — this affects both
  the fix approach and the confidence rating.

If a source file cannot be found for a reported element, keep the issue but note it as
**code not located** in the confidence field.

---

### Step 5 — Assign a confidence rating

Assign one of three levels to each issue based on corroboration:

| Rating | Criteria |
|--------|----------|
| **High** | Report failure + source code confirms the defect. Issue is static (not state-dependent). Two or more tools agree, or the failure is structural (e.g. missing attribute). |
| **Medium** | Report failure + source code found but issue may be partially dynamic (e.g. ARIA state that changes at runtime, contrast that depends on theme). Single tool. |
| **Low** | Report failure only; source code not located, or issue is highly state-dependent (e.g. only present when a modal is open). May be a false positive from a snapshot capture. |

---

### Step 6 — Rank by user impact

Order the final issue list by the following priority, resolving ties by number of pages
affected (descending):

1. **Critical** impact + Level **A** failures (highest)
2. **Critical** impact + Level **AA** failures
3. **Serious** impact + Level **A** failures
4. **Serious** impact + Level **AA** failures
5. **Moderate** impact + Level **A** failures
6. **Moderate** impact + Level **AA** / Best Practice
7. **Minor** impact (lowest)

Within each band, issues that affect all pages or every page in the audit outrank those
affecting a subset.

---

### Step 7 — Propose fixes

For every issue, write a concrete, minimal remediation. Fixes must:

- Reference the exact file path(s) identified in Step 4.
- Be presented as diff-style code blocks (` ```diff `) showing before and after.
- Address the root cause, not just suppress the tool warning.
- Note when the fix involves a shared template / component so the developer understands
  the blast radius of a single change.
- When the defect originates in a third-party library, explain the library-level or
  wrapper-level fix (e.g. adding `role="combobox"` to override invalid ARIA from a directive).

Do **not** apply any fix — present proposals only.

---

### Step 8 — Write the output markdown

Determine the output path:

- If the user specified a path, use it.
- Otherwise, write to `ACCESSIBILITY-ISSUES.md` in the repository root.

The file must follow this structure exactly:

```
# Accessibility Issue List — WCAG 2.2 A/AA

> Generated by accessibility-review skill on <date>.
> Tools: <list of report files used>. Codebase: <root path>.

## Scope
<table: page name → URL/path, one row per audited page/view>

## Summary
<one-paragraph executive summary: total issues, critical count, AA-only count,
pages covered, and any systemic patterns observed>

## Summary Table
<table with columns: #, Issue title, WCAG SC, Level, Axe/Tool Impact, Confidence, Pages affected>

---

## Issues Ranked by User Impact

### 🔴 Critical  (repeat section heading for each impact band that has issues)

#### ISSUE-N — <short title>

| Field | Detail |
|-------|--------|
| WCAG 2.2 Criterion | X.X.X Name (Level A/AA) |
| Tool rule | `rule-id` |
| Tool impact | Critical / Serious / Moderate / Minor |
| Confidence | High / Medium / Low — <one sentence reason> |
| Pages affected | Page A, Page B |
| Source file(s) | path/to/file.html (line N) |

**Description**
<2–4 sentences explaining the problem and its impact on AT users>

**Failing elements**
<code block with representative element(s) from the report>

**Proposed fix**
<diff-style code block, referencing exact file and context>

---
(repeat for each issue)

## Notes
<caveats: snapshot vs live, dynamic state, third-party libraries, etc.>
```

---

## Quality checklist — before finishing

- [ ] Every issue has a WCAG 2.2 SC reference (or is labelled Best Practice).
- [ ] Every issue has a confidence rating with a reason.
- [ ] Proposed fixes reference actual file paths from the codebase.
- [ ] No source file has been modified.
- [ ] The output markdown has been written to the specified or default path.
- [ ] The summary table is present and counts match the detailed issue list.
